# 接口速览卡标准（V2 提炼版）

> 来源：《接口速览卡-标准与示例V2》（V2 / 2026-11-09）。
> 本文件只保留生成卡片时需要执行的规则；示例与评审记录留在原文件，不复制过来。
> 定位：面向使用者的速览标准，不替代接口设计说明书、OpenAPI 契约、代码或验收记录。

## 一、卡片描述的对象必须明确

卡头写清七项，缺项照实标注：

| 项 | 要求 |
| --- | --- |
| 接口标识 / 版本 | 方法与完整路径；方案或代码版本（commit、契约版本） |
| 适用环境 | dev / test / prod，或"无真实部署环境" |
| 核对日期 | 实际核对日期，不是生成日期 |
| 维护人 | 人或团队；没有写"待指定" |
| 数据负责人 | 同上 |
| 规则负责人 | 同上 |
| 风险与验证 | 风险因子、级别、判定依据；验证到哪一步 |

设计文件只能证明"方案这样约定"，不能单独证明"系统已经这样运行"。源码只能证明相应版本的实现，不能单独证明目标环境已部署、配置正确或测试通过。来源冲突时列为待确认，不要自己把某份材料升级为运行结论。

## 二、三态标注（关键结论必须带）

连续段落或整张表可共用一个标注，但必须说明覆盖范围；局部例外单独标。

| 标记 | 最少写什么 |
| --- | --- |
| `【事实】` | 结论范围、证据位置与版本、核对时间；业务决策另附确认人 |
| `【假设】` | 假设内容、采用理由、不成立时影响什么 |
| `【待确认】` | 缺什么、由谁确认、阻塞哪项判断或动作 |

无依据的字段、错误码、时长、表名、状态、调用方、恢复机制，**不得写成已确认事实**。缺负责人或证据时写"待指定 / 未提供"，不要编造姓名、链接、测试结果或批准记录。

## 三、八个区块

阅读顺序固定：先业务后技术、先链路后字段、先正常后异常。卡头与卡尾不计入 8 个区块。

| # | 区块 | 回答什么 | 写法约束 |
| --- | --- | --- | --- |
| 1 | 电梯摘要 | 干什么、谁在用、什么时候出问题 | 固定 3 行；每行内容 ≤30 字符（不计标签与 Markdown 标记）；调用方与第 4 块一致 |
| 2 | 它到底干什么 | 业务语言解释用途与成功含义 | 2–4 句 + 一句"用户动作 → 系统结果"；点出最易误解处；全文遵守封闭禁词表 |
| 3 | 什么时候用 / 别用 | 是否适合我的场景 | 固定四项：适用场景、前置条件、不适用场景及替代方式、误用风险 |
| 4 | 上下游链路 | 谁调我、我调谁、等待谁 | 链路条 + 依赖表；逐项写同步/异步、超时或投递时限、依赖强度及业务口径、失败影响 |
| 5 | 一次调用发生什么 | 处理顺序、事务边界、返回时点 | 编号步骤；主路径唯一标"同步返回点"；异步在实际分派位置标"异步分叉点"；提前拒绝与幂等重放作旁路 |
| 6 | 关键字段速查 | 要传什么、返回什么、错了怎么办 | **最多 8 个，不设下限**；标请求/响应位置、含义与约束、错用后果 |
| 7 | 状态与数据变化 | 改了谁、成功到哪一步 | 状态图或迁移表；每条边写触发条件和推动者；只读接口明确"无业务状态变更"及其他副作用 |
| 8 | 失败地图 + 3 个坑 + Q&A | 出事如何处理、如何回答同事 | 失败地图三列；固定 3 个坑、3–5 个问答；区分已知失败与结果未知 |

### 第 2 块封闭禁词表

`接口、字段、参数、实体、枚举、JWT、OpenAPI、HTTP、MQ、幂等、事务、ID、生产调度`

仅检查第 2 块正文全文，英文项不区分大小写；其他区块允许使用并解释技术术语。"节目编号""处理状态"等业务表达可以使用。通过禁词检查不等于已经易读，还须由目标读者确认。

### 第 3 块前置条件

必须同时覆盖：身份、功能权限、租户或资源权限、数据状态。只写"需要登录"不合格。

### 第 4 块超时

不能留空或只写"—"。异步链路可写"当前请求不等待消费；发送超时见配置；超过投递时限告警"。最终一致不等于没有发送超时、重试上限或积压处置。另需给出客户端、网关、服务三层的总耗时预算，且明确"下游单次超时 ≠ 整次请求最大耗时"。

### 第 5 块时间

超时只说明没及时拿到结果，不自动等于未执行、已回滚或可安全重试。这句话必须能在第 5 块或第 8 块找到落点。

### 第 6 块字段选择

优先：业务主键、决定性输入、容易被误读的状态值、区分错误类型的错误码、排障用的追踪标识。全量字段表放完整契约入口，不贴进卡片。

### 第 8 块失败地图三列

现象（可观察现象与错误码）｜原因或需核查的事项｜我该怎么办（查询标识、入口、重试条件、恢复动作）。必须覆盖：鉴权失败、业务冲突、输入错误、结果未知（超时/断连/5xx）、部分成功、下游延迟。

### 卡尾最小项

完整契约入口、证据与待确认、风险因子及分级依据、查询与监控入口、测试与发布/回滚记录。已有文档用链接承接，**不为凑齐栏目虚构系统能力**。

## 四、多接口时先做一页目录

最小四列：接口标识、一句话用途、谁在调、失败影响。可再展开关键下游、同步/异步、卡片状态。目录中的路由、调用方、同步/异步、故障影响必须与单卡一致。"只读"也可能影响业务查询，不能写成"失败无影响"。

## 五、自检（贴出去之前逐条过）

1. **对象与证据**：版本、环境、核对日期、维护及业务负责人明确；事实有出处、假设有范围、待确认有负责人和影响；设计与运行事实未混用。
2. **区块 1**：固定三行且每行 ≤30 字；调用方与链路一致。
3. **区块 2**：2–4 句 + 一句动作链；全文避开禁词表；交代用途、成功含义、最易误解处。
4. **区块 3**：四项完整；同时检查功能权限与数据范围；替代入口真实可用或明确标为待确认。
5. **区块 4**：每项依赖的等待关系、超时/投递时限、依赖口径、失败影响齐全；总耗时与单次下游超时未混为一谈。
6. **区块 5**：主路径仅一个同步返回点；异步分叉点在实际生效位置；错误与幂等旁路单列；事务内外边界与恢复方式一致。
7. **区块 6**：关键字段 ≤8；完整契约入口真实；响应状态与重放快照的含义和步骤、问答一致。
8. **区块 7**：每条状态边有触发条件和推动者；成功与失败出口完整无悬空线；本服务写入与下游写入分清；未知结果不被当成确定失败，晚到更新不倒退状态。
9. **防重与重试**：同键同载荷、同键异载荷、处理中重放、无键同名、换名换键、窗口过期各有明确结果；自动重试有实际去重依据。
10. **区块 8**：失败地图给出可执行动作，含调用方先超时与部分成功；固定 3 个坑、3–5 个问答；可用业务编号与追踪标识定位。
11. **可观测与交付**：查询、日志、监控、错误码、兼容、测试、发布回滚证据有入口或明确缺口；未把"写完卡片"写成"验证通过"。
12. **目录与关联**：前缀、用途、调用方、可修改范围、失败影响与单卡一致；旧口径材料列出待同步项。

自检只证明卡片完整性与内部一致性，**不等于真实接口测试、业务验收或上线批准**。

## 六、从代码生成卡片时的特有约束

标准的示例是基于设计的构造示例；本技能是基于代码生成，因此额外遵守：

- 路由必须来自代码中的真实注解/注册，类级前缀与方法级路径要拼接后核对，不要只取注解字符串。
- 字段来自 DTO/VO/TS 类型/schema 的真实定义；取不到就写待确认，不要按名字猜类型。
- 错误码来自异常映射、错误码枚举或统一返回体包装；只看到 `throw new RuntimeException` 就写"未登记错误码"。
- 超时、重试、线程池、幂等窗口来自配置类与配置文件；配置里没有就写"未配置 / 待确认"，不要写行业默认值。
- 调用方来自路由注册、网关配置、前端 api 目录；**没有证据就不要列"定时任务""历史脚本"作为调用方**。
